# 6. РАЗРАБОТКА СЕРВЕРНОЙ ЧАСТИ

Серверная часть приложения реализована на языке программирования Python с использованием фреймворка FastAPI. Выбор данного фреймворка обусловлен его удобством при создании REST API, поддержкой автоматической генерации документации и возможностью быстрого развертывания серверного приложения.

Разработанный сервер обеспечивает доступ к базе данных классификатора комплектующих ПК и серверов посредством HTTP-запросов. Через сервер реализуются операции создания, изменения, удаления и перемещения категорий классификатора, а также операции работы с конечными комплектующими и их спецификациями.

Приложение развернуто с использованием Docker и описано в файле конфигурации `docker-compose.yml`. Система состоит из двух контейнеров:

- контейнера базы данных PostgreSQL;
- контейнера серверного приложения FastAPI.

Подключение серверной части к базе данных осуществляется внутри Docker-среды. При запуске контейнеров автоматически создается база данных, формируется структура таблиц и подготавливается корневая вершина классификатора. Благодаря этому после запуска приложения система сразу готова к работе без выполнения дополнительных ручных операций.

Для взаимодействия с серверной частью используется REST API. Дополнительно FastAPI автоматически предоставляет Swagger UI, что упрощает тестирование и демонстрацию работы системы. Документация API доступна по адресу `/docs`.

В таблице 2 рассмотрим реализованные методы подробнее.

**Таблица 2 - Реализованные методы HTTP**

| Метод | URL | Описание |
| :--- | :--- | :--- |
| `GET` | `/info/ping` | Проверка доступности серверного приложения |
| `GET` | `/database/info` | Получить краткую информацию о состоянии базы данных |
| `POST` | `/database/tables/create` | Создать таблицы базы данных и подготовить структуру хранения |
| `GET` | `/database/tree` | Получить полное дерево классификатора вместе с конечными комплектующими |
| `GET` | `/database/specifications` | Получить справочник уникальных спецификаций |
| `POST` | `/database/categories` | Создать новую вершину классификатора |
| `PATCH` | `/database/categories/{category_id}` | Изменить название вершины классификатора |
| `PATCH` | `/database/categories/{category_id}/move` | Переместить вершину в другую ветку дерева |
| `DELETE` | `/database/categories/{category_id}` | Удалить вершину классификатора |
| `POST` | `/database/products` | Добавить новый продукт в выбранную категорию |
| `PATCH` | `/database/products/{product_id}` | Обновить данные продукта |
| `PATCH` | `/database/products/{product_id}/move` | Переместить продукт в другую категорию |
| `DELETE` | `/database/products/{product_id}` | Удалить продукт |

Проведем тестирование разработанной серверной части. Для начала осуществляется запуск приложения с использованием Docker Compose (Рисунок 7).

**Рисунок 7 - Запуск сервера**

После успешного запуска становится доступна работа с базой данных и HTTP API. На первом этапе можно выполнить запрос создания таблиц базы данных, после чего сервер автоматически подготовит структуру хранения данных и корневую категорию классификатора.

Далее через метод `POST /database/categories` возможно добавление новых узлов дерева, например категорий "Комплектующие для ПК", "Серверные комплектующие", "Процессоры для ПК", "Серверные процессоры" и других разделов каталога (Рисунок 8).

**Рисунок 8 - Добавление нового узла классификатора**

После создания категорий можно выполнить запрос `GET /database/tree` и получить полную структуру классификатора вместе со всеми дочерними категориями. Это позволяет проверить корректность добавления узлов и их привязку к родительским вершинам (Рисунок 9).

**Рисунок 9 - Получение дерева классификатора**

Следующим этапом выполняется добавление конечных комплектующих. Для этого используется метод `POST /database/products`, который позволяет создать новый товар в выбранной категории и одновременно задать набор характеристик. Если указанная характеристика уже существует в справочнике, сервер использует существующую запись; если не существует, она создается автоматически (Рисунок 10).

**Рисунок 10 - Добавление нового продукта**

Для проверки корректности работы механизма спецификаций используется метод `GET /database/specifications`, который выводит справочник всех уникальных характеристик, добавленных в систему (Рисунок 11).

**Рисунок 11 - Получение справочника спецификаций**

Рассмотрим изменение структуры дерева. Для этого может быть использован метод `PATCH /database/categories/{category_id}/move`, который позволяет изменить положение выбранной категории внутри классификатора. После выполнения данной операции можно повторно получить дерево через `GET /database/tree` и убедиться, что категория была перемещена в новую ветку (Рисунок 12).

**Рисунок 12 - Перемещение вершины классификатора**

Аналогично возможно изменение данных существующей категории или товара. Для категории используется метод `PATCH /database/categories/{category_id}`, а для продукта - `PATCH /database/products/{product_id}`. Это позволяет изменять названия, описания, цены, количество и набор характеристик без удаления существующих записей (Рисунок 13).

**Рисунок 13 - Изменение данных категории или продукта**

Если внесенные изменения больше не требуются, система позволяет удалить объект с помощью метода `DELETE`. Для категорий реализована дополнительная проверка: вершина не может быть удалена, если в ней содержатся дочерние категории или товары. Такая проверка предотвращает нарушение целостности классификатора (Рисунок 14).

**Рисунок 14 - Удаление объекта классификатора**

После выполнения операций удаления или перемещения можно повторно выполнить запрос на получение дерева и убедиться, что структура данных изменилась корректно и соответствует ожидаемому состоянию (Рисунок 15).

**Рисунок 15 - Проверка результата после выполнения операций**

Таким образом, по результатам тестирования можно сделать вывод, что серверная часть приложения корректно реализует все основные функции взаимодействия с классификатором. Реализованные HTTP-методы обеспечивают управление категориями, товарами и спецификациями, поддерживают работу с полной древовидной структурой и позволяют выполнять демонстрацию системы через Swagger UI. Это подтверждает корректность реализации серверной части и ее соответствие поставленным требованиям.
